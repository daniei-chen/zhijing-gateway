# A. 产品定位（从代码反推）

## A.1 它是什么

一个**多协议 AI API 网关 + 额度转售平台**。三件事同时成立：

1. **协议面**：把 Anthropic Messages、OpenAI Chat Completions / Responses、Gemini `v1beta`、以及若干厂商私有协议（Codex `backend-api/codex`、Antigravity、Grok、Seedance）收进同一套鉴权与计费。证据：`internal/server/routes/gateway.go` 里 127 条数据面路由，按协议族分组（`/v1`、`/v1beta`、`/backend-api/codex`、`/antigravity/v1`）。
2. **账号面**：上游不是 API key 直连，而是**订阅账号池**（ChatGPT Pro、Claude、Gemini 等），靠 `accounts` + `extra.upstream_model_metadata` 调度，按模型把请求分给"有资格服务"的账号。证据：`ent/schema/account.go`，`internal/service/account.go`，调度入口 `internal/service/scheduler*`。
3. **商业面**：按美元计费（不是按 token 计限流）、分组配额、兑换码、订阅计划、支付渠道（Stripe / 支付宝 / 微信 / 易支付）、模型广场。证据：`ent/schema/{api_key,group,subscription_plan,redeem_code,payment_order}.go`，`internal/payment/`。

所以它不是 LiteLLM 那类"给开发者做代理"的东西，也不是 pure gateway：**它把"订阅额度"当成库存来分发和计费**，用户买的是额度，不是模型访问权。这解释了后面很多设计取舍（按美元限流而非按 token、账号池而非 key 池、计费后扣而非预扣）。

## A.2 入口

单一二进制，一条 `main`：`backend/cmd/server/main.go:56`。三种启动形态由 `setup.NeedsSetup()` 分叉（`main.go:82-95`）：

| 形态 | 触发 | 行为 |
|---|---|---|
| CLI 向导 | `-setup` | `setup.RunCLI()`（`main.go:69`） |
| 自动初始化 | 首启 + `AUTO_SETUP=true` | `AutoSetupFromEnv()` 后继续起主服务（`main.go:85`），Docker 走这条 |
| 网页向导 | 首启、无 AUTO_SETUP | `runSetupServer()`（`main.go:98`）：独立 gin，只挂 Recovery/CORS/SecurityHeaders + setup 路由 + 内嵌前端；绑定地址默认回环，非回环打 WARNING（`main.go:114-120`），要求一次性 token |

主服务装配：`runMainServer()`（`main.go:160`）→ `config.LoadForBootstrap()` → `logger.Init` → `initializeApplication`（wire 生成，`cmd/server/wire_gen.go:35`，798 行，是依赖图的唯一正确入口）。插件管理器与 Prompt Audit 都**降级启动**：起不来只打日志、服务继续（`main.go:188-200`）。退出用 `SIGINT/SIGTERM`，默认 8 秒排空（小于 Docker 10 秒），`SHUTDOWN_TIMEOUT_SECONDS` 可调到 600（`main.go:236-268`）。

版本号 `//go:embed VERSION` + ldflags 注入，缺注入时显示 `0.0.0-dev`/`unknown` 而不是空串（`main.go:30-53`）。

## A.3 一个请求从进来到出去

全局中间件 11 层（顺序即执行顺序）：`Recovery` → `Metrics` → `RequestLogger`（X-Request-ID）→ `SessionBindingContext` → `Logger` → `CORS` → `SecurityHeaders` → `ServerTiming` → 内嵌前端注入 → 每 socket 读 idle deadline → 每次写/flush deadline（`internal/server/http.go:53-165`）。刻意**不设**整条流的 `WriteTimeout`/`ReadTimeout`（`http.go:117-127`），体积上限走 `MaxBytesHandler`。

数据面 `/v1` 组内顺序（`routes/gateway.go:180-191`）：`bodyLimit` → `clientRequestID` → `opsErrorLogger` → `endpointNorm` → **`apiKeyAuth`** → `groupModelAllowlist` → `compositeTarget` → `requireGroupAnthropic`。127 条数据面路由全部经过 `apiKeyAuth`（复核命令见 §C）。

`apiKeyAuth` 内部 14 步（`middleware/api_key_auth.go:39`）：IP 滥用计数 → 头体积上限 → **拒绝 `?key=`/`?api_key=`** → 取 key（Bearer / x-api-key / x-goog-api-key）→ Redis 查 key（singleflight，只读）→ 状态 → **IP ACL**（`GetSecurityClientIP` 按 `trust_forwarded_ip_for_api_key_acl` 决定信不信转发头）→ 用户存在/激活 → 分组可用 → skipBilling 判定 → simple 模式早返回 → 订阅加载 → 计费前置校验（余额/订阅窗口）→ 写 ctx + **`TouchLastUsed`（第一处 DB 写）**。

handler 主流程（`POST /v1/messages`，`handler/gateway_handler.go:125`）：读体 → 解析 → 模型/推理强度策略 → 渠道映射 → 版本检查 → 白名单/平台检查 → 内容审计 → **用户并发槽位**（等槽期间 10s 一次 SSE ping）→ 计费二次校验 → 在途余额预留 → 粘性会话 hash → 选号 + **账号并发槽位** → 上游转发（重试/failover）→ 记用量。

**结论：鉴权之前没有写库、没有计费、没有上游调用**（逐项核实，`inbound-auth.md` §2.1）。这是一条干净的分界。

# D. 缺陷与风险清单

## D.0 分级口径（本轮按大队长的定义重排）

> **P0 = 普通用户（不需要管理员会话、不需要特殊配置）能造成资金损失、数据丢失或数据外泄。**
