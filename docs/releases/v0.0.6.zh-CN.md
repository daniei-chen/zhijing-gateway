# v0.0.6 · 稳定性与安全修复

本版是**后端修复版**，包含 6 个独立补丁，全部已在生产验证。前端与 v0.0.4/v0.0.5 一致，未改动。相对 v0.0.5 的源码差异是 **13 个文件（9 改 + 4 新增）**，已打包为可干净应用的 patch。

> ⚠️ **含两条行为变更**，升级前请阅读「行为变更」一节。

## 修复内容

| 补丁 | 问题 | 实际行为 |
| --- | --- | --- |
| P1-01 | 本地并发拒绝时 `Retry-After` 固定 2 秒 | 改为 **30 秒**，与排队窗口 `maxConcurrencyWait` 对齐。实测一次上游请求的 `duration_ms` P90 为 38–52 秒，2 秒的建议会让守规矩的客户端立刻重试进同一个饱和服务，形成「429 → 2s → 更饱和」的正反馈 |
| P1-02 | 告警 SLA 指标无最小样本门槛 | 加 **20 个样本**门槛：样本不足时不评估。线上 7 天 260 次 SLA 告警的 `metric_value` 全部是 `1/N` 序列（100/50/33.33/25/12.5…），即分母只有 1–18 个请求；其中 P0 规则「错误率极高」92 次里有 39 次是「1 个请求 1 个错」 |
| P1-03 | 资金异常无监控 | 新增 3 个告警指标：`billing_leakage_count` / `billing_leakage_amount_usd` / `billing_dedup_gap_count`。**需在 `ops_alert_rules` 建规则后才会告警** |
| P2-01 | 余额缓存可能被旧快照覆盖新扣减 | 回填改用 `SETNX`：缓存未命中回源 DB 的快照不再无条件覆盖缓存。10 个无序 worker 下，旧快照可能晚于增量扣减执行，把 90 覆盖回 100，直到 TTL（≈5 分钟）过期才自愈 |
| P2-02 | `/admin/system` 三个高危写操作无 step-up | `update`/`rollback`/`restart` 挂上 step-up 2FA 门控。`update` 会下载 release 包并覆盖当前二进制，等于把「管理员 API Key」升级成「主机代码执行」——危害比已有保护的 backup restore 更大，此前却完全裸奔 |
| P2-03 | 告警规则 `last_triggered_at` 从不回写 | 全仓库只有 SELECT 没有 UPDATE，导致规则列表永远显示「从未触发」。线上实测 8 条规则全为 NULL，而事件表已有 298 条记录。现改为事件创建后回写 |

## 行为变更（升级前必读）

1. **客户端重试间隔变长**：本地并发拒绝的 `Retry-After` 从 2 秒变 30 秒。客户端会等更久才重试——这是刻意的，用来打断重试风暴。
2. **低流量时段 SLA 类告警会静默**：5 分钟窗口内不足 20 个请求时不评估。CPU / 内存 / 并发队列 / 账号类告警不受影响，仍全程生效。
3. **P2-02 默认不生效**：`step_up_enabled` 当前为 false、且管理员需先绑定 TOTP。若直接开启而管理员无 TOTP，会把管理员锁在受保护接口之外。启用顺序见 `docs/security/step-up-rollout.zh-CN.md`。

### 与 v0.0.5 的验证范围差异（如实说明）

v0.0.5 跑了全 tag 编译、`-race`、`govulncheck`、真实 PG+Redis 集成套件、旧 UI 端点回放。**本版未重跑这些**，验证集中在受影响的三个包的单测 + 静态检查 + 补丁可应用性 + 生产实跑。原因是本次改动不含 schema 变更、不涉及前端、不触碰并发原语（唯一的并发相关改动是 SETNX，语义上比 SET 更保守）。

`not_covered` 已在 `validation-v0.0.6.json` 中显式列出。
