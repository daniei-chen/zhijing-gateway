对象：`Wei-Shaw/sub2api`，diff 起点 `530c5e3a4`（11-11 那次审计记录的上游 HEAD，也是欠账的真实起点），终点 `4233cc3`（11-27）。
实测（本地 fetch 上游后自己算的，不是抄文档）：**468 个提交、694 个文件（175 新增 / 519 修改）**，其中 **588 在 backend、92 在 frontend**。

两边都改过的文件 **351 个**（这是冲突上界；试合并的实际冲突是 **120 个**，其余是品牌改名造成的"假冲突"：本仓库把 1,778 个文件做了机械改名，git 会把它当成两边都改）。

## 0. 为什么必须分片（根因，不是流程偏好）

本仓库**不是 GitHub fork，与上游没有共同祖先**：

| 证据 | 结论 |
|---|---|
| `git cat-file -t 10ba8f9b4` → `fatal: could not get object info` | 上游基线的提交对象在本地不存在 |
| 本地唯一 root 是 `e5247df`，提交信息自报 `source tar.gz @ 6b4b37db (0.2.20)` | 仓库从源码压缩包导入 |
| `local-v002-baseline.json` 是导入时 78 个文件的 sha256 指纹 | 它是三方合并的参照物，不是上游基线 |

所以 **`git merge upstream/main` 在任何时候都是错的**：没有共同祖先，合并等于用上游整棵树覆盖本地，本 fork 的硬化（hash 锁、受保护字节、门禁清单）会静默消失，git 也不会报冲突。唯一安全的路径是 `fork-manifest.json` 那套逐文件判定 + 按文件三方合并，而它必须分片做。

## 2. 顺序与理由

1. **S1 安全修复先走，且要完整**。其中 `ce86c1b30` 关掉的"重复字段"绕过正是审计的 P0-1：**止血 PR 先合我们的最小实现，S1 落地时删掉我们的、换上游那套（连同它的测试），不留两套检测**。我们 PR 里的负例要么迁过去、要么在 commit 里写明被上游哪条测试取代。
2. **S2 排在第二，但这三天只出方案**。冲突 76 个，方案要逐文件写明"取上游 / 保留本地 / 混写"，并标出哪些本地硬化会被覆盖。
3. **S5、S6 与 S2 的方案阶段并行**：生成物只要 regenerate，基建是 Go 版本与 CI 配置，都不碰业务逻辑。
4. **S3 有余力再做**：冲突只有 6 个，但 11 个安全提交落在这一层，S1 先做会削掉一半。
5. **S4 最后**：前端 92 个文件里 20 个两边都改，且依赖后端 API 形状先稳定。

## 3. 每片验收口径（统一）

一片一个 PR，每片必须带：

1. `go build ./...`、`go test -tags=unit ./...`、`go test -tags=integration ./...`，实数贴进 PR。
2. **回退点**：PR 描述写明"这片回退受影响的文件清单"和"回退后哪些行为会变"。
3. **不许静默回退本地硬化**：PR 里有一节 `fork mechanisms preserved`，逐条列出本 fork 的机制（hash 锁、受保护字节、门禁清单、fork-manifest）在本片里怎么处理。
4. 安全片额外要求：每条上游安全修复挂一个能证伪的测试，或指出上游已带测试并给出文件。
5. 冲突 >20 的片：先交只含文档的方案 PR，批准后才动代码。
