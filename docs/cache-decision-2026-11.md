# 决策记录：不做响应缓存（2026-11-26）

## 结论

**不做响应缓存。** 从候选清单移除，不再作为"下一轮要做的事"挂着。

## 为什么（数据，不是判断）

连续四轮把"响应缓存"排在候选第一位，理由是通用的"缓存能省钱、能降延迟"。
这一轮先查了真实流量再决定，结论和直觉相反：

```
近 7 天请求总数：37,903
其中流式：       37,895  （99.98%）
其中非流式：          8  （0.02%）
```

**缓存只能服务非流式请求** —— 流式响应必须逐 token 推给客户端，把整段缓存重放会破坏
首字延迟语义和客户端的流式处理，等于改变产品行为。也就是说：即使缓存做得完美，
它能覆盖的流量上限是 0.02%。

为了 7 天 8 次请求去建一套包含"键设计、隔离、失效、计费口径"的子系统，投入产出完全不成立。

## 顺带确认的两件事

1. **TTFT 慢不是网关的锅**：近 1 天按模型看，`gpt-6.1-sol` 平均首字 11.6 秒、
   `gpt-6-luna` 3.0 秒 —— 差异由模型决定。当前只有一个上游账号（`account_id=2`），
   无法做账号间的横向对比，所以"调度选错账号"这一假设既无法证实也无法证伪，
   也就没有依据去改调度。
2. **错误分布健康**：近 7 天 243 条错误里，`model_not_found` 37 条几乎全是探针用的
   假模型名（`zzz-split`、`gpt-probe-does-not-exist` 等），真实用户只有 4 次请求了
   `gpt-5.1` 这个已下线的模型。

## 什么情况下应该重新考虑

不是"以后都不做"，而是有明确触发条件才回来看：

- 非流式请求占比持续超过 20%（说明客户端用法变了）
- 出现批量/离线类调用场景（这类天然是非流式的，才真正吃缓存）
- 上游按 token 计费且我方成本压力显著上升，同时有办法只缓存确定性输出（`temperature=0`）

在触发条件出现之前，讨论缓存就是浪费一轮迭代。

其实永远是空的"这类假观测。
