# 图片定价漏配的成交口径（`image_price_defaulted`）

图片请求按张计费，一次调用就是一次真实成本。渠道/分组定价行存在、但价格字段一个都没填时，
历史实现会出现四种答案：走 token 计费得 $0、走 token + 分组按张开关得默认图价、走按次计费得
$0、走渠道相对价缺失时又各不一样。同一件事四种口径，账上还会留下无声的 $0 成交。

本页记录现在的统一口径，以及运维怎么发现和修掉漏配。

## 判定顺序

一次图片请求（`image_count > 0`）按下面的顺序定价，没有新开关：

1. **有可用单价** —— 渠道/分组/分组图价里配了价格，就按它成交。行为不变。
   - 「配过」只看价格字段是否填写；显式配 0（免费）也算配过，是运营者的选择。
2. **没有可用单价，且 `billing.inflight_reservation.fail_closed_on_unpriced = true`** —— 失败关闭：
   算价失败，请求按既有的算价失败链路处理（4xx + `billing_failures` 留痕）。
3. **没有可用单价，且该开关为 false（默认）** —— 按默认图价成交：
   分组图价 → 模型目录价 → 内置默认图价（`0.134`/张，2K 1.5 倍、4K 2 倍），
   并在 `usage_log.billing_tier` 写入 `image_price_defaulted` 标记。

没有渠道/分组定价行的模型（`resolved == nil`）不算漏配：它们本来就按目录价或内置默认图价成交，
不打标记。

## 用户会看到什么

- 漏配的图片渠道不再免费：请求成功，但按**默认图价**计费（默认 $0.134/张起）。
  这是向用户收钱的行为变化，发布说明里要写清楚。
- 运维把开关打开后，同一批请求会变成失败（4xx），直到价格补上。

## 运维怎么发现和修

- 管理端「用量」列表的计费模式列会出现**默认价**徽标（`billing_tier = image_price_defaulted`）。
- `GET /api/v1/admin/usage?billing_tier=image_price_defaulted` 只返回按默认价成交的行，
  用来回答「今天有多少笔按默认价成交」；非法取值返回 400。
- 用户侧 `/usage` 故意不返回 `billing_tier`：这是运营侧标记，不暴露给终端用户。
  也就是说，未配价的渠道被按默认图价计费时，用户自己看不见——发布说明必须写明
  「未配价的渠道按默认图价计费」。
- 修法二选一：给渠道定价行补上 `per_request_price` / token 单价，或给分组补 `image_price_1k/2k/4k`。
- 想让漏配直接变硬错：打开 `billing.inflight_reservation.fail_closed_on_unpriced`
  （该开关同时决定转发前的无价拦截，默认已为 `true`）。

## 简易模式（`run_mode: simple`）

简易模式只记 usage、从不扣费，因此**永不失败关闭**：漏配图片一律按默认图价记账
（`actual_cost` 仅作分析，不产生扣款）。这个口径是配合部署方的，不是用户可切换的通道。
